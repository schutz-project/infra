# 직원 포털 A — 간단한 장애 시나리오 계획

상태: **계획 / 팀 검토 필요**. 이전 장애 재현 경험은 있지만 아래 3개를 이번 발표 버전에서 모두 검증했다는 뜻은 아니다.

## 목표
복합 장애에 앞서 모니터링 플랫폼이 단일 장애를 감지하고, 운영자가 AI 없이 근거를 확인해 복구하는 흐름을 보여준다.

| 후보 | 예상 현상 | 확인할 증거 | 복구 및 검증 |
| --- | --- | --- | --- |
| 직원 검색 응답 지연 | HTTP 200이나 응답시간이 기준 초과 | 요청 지연시간, 앱/DB 로그, 사건 생성 및 알림 | 원인 제거 후 정상 응답시간·사건 종료 확인 |
| 반복 로그인 실패 | 인증 실패 이벤트 누적 | 로그인 실패 이벤트, 탐지 규칙, 사건/알림 | 테스트 중단, 정상 로그인 및 사건 상태 확인 |
| HTTP 500 | 서버 내부 오류 응답 | HTTP 상태, API·Nginx 로그, 사건/알림 | 원인 복구 후 HTTP 정상 응답 확인 |

### 기존에 사용한 지연 기준
과거 실습에서는 30초 간격 점검, 2초 초과 3회 연속 사건 생성, 정상 2회 연속 복구 기준을 사용했다. **최신 관리 웹 규칙과 동일한지는 시험 전에 확인해야 한다.** 로그인 실패 및 HTTP 500의 최신 탐지 조건도 미확정이다.

## 멘토 피드백 반영
멘토링에서는 Compose 환경변수를 바꾸거나 애플리케이션에 인위적 지연을 삽입하는 방식이 실제 운영 장애의 원인으로는 설득력이 약할 수 있다는 의견이 있었다. 따라서 **Docker Compose 자체를 부하 발생 도구로 설명하지 않는다.** 재현 방식은 팀원과 협의해 결정한다. JMeter는 실제 HTTP 요청 부하를 만들 수 있지만 반드시 지연이나 오류를 발생시키는 것은 아니다.

## 실행 전 점검
- [ ] 시나리오별 실제 장애 원인과 재현 방법을 팀과 합의
- [ ] 최신 탐지 규칙 및 테스트 계정·데이터 확인
- [ ] 공유 서비스 EC2의 B·C 영향과 복구 절차 확인
- [ ] 기준 상태(응답시간, CPU/메모리, 로그, 서비스 정상 응답) 기록
- [ ] 시나리오별 발생→탐지→수동 분석→복구→사건 종료 증빙 수집
- [ ] 실행 시각, 로그, 스크린샷, 조치 결과를 별도 시험 기록에 정리

운영 데이터 훼손, 비밀번호 공개, 임의의 전체 서비스 중단을 피하고 테스트 범위를 팀원과 사전 조율한다.
