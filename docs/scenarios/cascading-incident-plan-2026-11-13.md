# A→B·C 복합 장애 시나리오 — 발표용 계획

상태: **멘토 제안 방향을 채택한 계획**. 실제 장애 전파·원인 및 JMeter 사용은 검증 전이다.

## 목적
단일 서비스 장애는 운영자가 비교적 빠르게 분석할 수 있지만, 여러 서비스에 연쇄적으로 문제가 발생하면 최초 원인과 전파 순서를 찾기 어렵다는 점을 보여준다. 이후 AI 분석을 이용한 원인 상관관계 파악과 비교한다.

## 목표 흐름 (가설)
1. 직원 포털 **A**에 많은 요청이 발생한다.
2. A의 처리 로직·DB·공유 EC2 자원에 병목이 발생할 수 있다.
3. 자원 경합 등 **실제 확인된 연결 원인**을 통해 홈페이지 **B**와 커뮤니티 **C**에도 응답 지연 또는 장애가 발생한다.
4. 운영자는 서비스별 오류 시각, CPU·메모리, 요청량, DB 상태, 로그를 비교하여 최초 원인을 추적한다.
5. 같은 사건에 대해 AI 분석 결과와 수동 분석의 근거·시간을 비교한다.

**주의:** A·B·C가 같은 EC2를 사용한다는 사실만으로 A 부하가 B·C 장애를 반드시 일으키는 것은 아니다. B·C가 동일 DB를 공유한다고도 확인되지 않았다. 멘토가 설명한 공유 DB 연쇄 장애는 **가능한 예시**이지 현행 구조의 확정 사실이 아니다.

## 역할 및 확인
- [ ] 팀과 요청 부하 생성 도구(JMeter 등), 테스트 강도, 종료 조건 합의
- [ ] A/B/C의 실제 의존 관계와 컨테이너 자원 제한 확인
- [ ] 서비스별 정상 응답 및 모니터링 수집 상태 확인
- [ ] 안전한 소규모 부하부터 단계적으로 시험
- [ ] A→B→C 장애 전파가 실제로 일어났는지 시간순으로 검증
- [ ] 전파되지 않으면 원인을 분석하고 시나리오를 조정하되 결과를 과장하지 않기
- [ ] 수동 원인 분석, AI 분석, 복구 및 정상화 기록

## 안전장치
- 팀원과 사전 협의 없이 공유 EC2에 고부하를 발생시키지 않는다.
- 테스트 계정·데이터를 사용하고, CPU·메모리·오류율·응답시간의 중단 기준을 사전에 정한다.
- 서비스 복구 절차와 담당자를 지정한 뒤 수행한다.
