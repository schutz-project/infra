# SCHUTZ — CPU 과부하 장애 시나리오 (작업 기록)

기록일: 2026-11-17 (KST)  
범위: 직원 포털 A CPU 과부하 및 홈페이지 B / 커뮤니티 C 영향 범위 분석

> 이 문서는 프로젝트 진행 중 실제 관찰한 내용과 대화에서 확인한 조치에 기반한 **작업 기록**입니다. GitHub에 등록되지 않은 서버 내부의 최신 Compose, k6, Prometheus, 웹 수정 원본을 자동 백업한 것은 아닙니다. 운영 서버의 최신 파일과 일치하는지는 별도 확인이 필요합니다.

## 시나리오 목표

1. 격리된 테스트 환경의 직원 포털 A 검색 API에 k6로 실제 CPU 작업 부하를 발생시킵니다.
2. CPU 사용률, 검색 응답시간(P95), 요청량(RPS), 5xx 오류율을 확인합니다.
3. 같은 시각 홈페이지 B와 커뮤니티 C가 정상인지 비교합니다.
4. Prometheus 및 SCHUTZ 자체 운영 대시보드에서 장애 탐지, 사건 생성, Slack 알림을 확인합니다.
5. 부하가 사라진 후 복구 상태 확인과 관리자의 수동 사건 종료를 검증합니다.

## 사용한 구성요소

- AWS EC2: 서비스 서버 / 모니터링 서버
- Docker: 테스트 직원 포털 A, 홈페이지 B, 커뮤니티 C
- FastAPI: 직원 검색 API 및 서비스별 API
- k6: 검색 API 부하 발생
- Prometheus: 메트릭 수집 및 CPU 경보 평가
- SCHUTZ 관리 웹/워커: 사건 및 복구 상태 관리
- Slack: 장애·복구 알림
- 운영 대시보드: 자원 지표와 서비스별 영향 범위 확인

## 확인된 진행 내용

| 단계 | 확인 결과 |
| --- | --- |
| 테스트 서비스 구성 | A·B·C 테스트 서비스 구성 및 접근 확인 |
| CPU 부하 테스트 | k6 부하 시 A의 CPU 사용률과 검색 지연 증가 확인 |
| 응답 지연 | 앞선 시험에서 검색 API P95 약 11.42초까지 증가한 결과 보고 |
| 영향 범위 | 시험 당시 홈페이지 B와 커뮤니티 C 정상 응답 유지 확인 |
| 탐지/알림 | Prometheus CPU 경보, SCHUTZ 사건 생성, Slack 알림 확인 |
| 복구 | k6 종료 후 CPU/응답시간 자연 정상화 확인 |
| 사건 종료 | 관리 웹 수정 후 '복구 확인 · 사건 종료' 가능함을 검증 |

**주의:** k6가 종료돼 CPU 부하가 저절로 낮아진 것은 **서비스의 자연 복구**입니다. 엔지니어가 서버 리소스나 설정을 변경해 직접 원인을 제거한 시나리오는 아직 별도 구현·검증하지 않았습니다. SCHUTZ의 경보 자동 정상화와 관리자의 사건 수동 종료도 서로 다릅니다.

## 운영 화면 개선 사항 (2026-11-17 확인 범위)

- EC2 두 대의 CPU/메모리/디스크 지표 확인
- 시험용 직원 포털 A(정상/부하), 홈페이지 B, 커뮤니티 C CPU 화면 확인
- CPU 장애 탐지 시각인 **2026-11-16 23:47:01 KST**을 서버 CPU 그래프에 표시하는 기능은 팀원분이 구현했다고 공유
- B `/api/organization`, C `/api/questions`의 경로별 P95·RPS·5xx 지표는 팀원분이 반영했다고 공유했으나 **동일한 시간 범위에서 실측값 크로스체크는 별도 수행 대상**

## 저장소 및 보안

GitHub의 기존 코드와 서버에서 실행 중인 코드는 서로 다를 수 있습니다. 특히 기존 `management-web` 저장소의 `management/alert_policy.py`에는 CPU 규칙 등록이 없는 것을 2026-11-17에 확인했으므로 최신 서버 수정을 가져오기 전까지 **기존 코드가 고쳐졌다고 간주하지 마세요.**
