# CPU 과부하 장애 흐름 및 검증 기록

## 1. 정상 기준선

- 직원 포털 A 검색 API 정상 응답 확인
- B 홈페이지 및 C 커뮤니티 API 정상 응답 확인
- A/B/C 컨테이너 상태 및 CPU 사용률 기록
- SCHUTZ 운영 대시보드와 Prometheus 메트릭 수집 상태 확인

## 2. 부하 및 장애 탐지

- 격리된 테스트 대상 **직원 포털 A 검색 API**에 한해 k6 부하 발생
- A CPU 사용률 및 P95 검색 응답시간 상승 확인
- Prometheus CPU 경보 및 SCHUTZ 사건 생성 확인
- Slack 장애 알림 확인
- **B/C의 CPU, 응답시간 P95, RPS, 5xx 지표**를 같은 시간 범위에서 확인해 영향 범위 판단

기록된 테스트 관찰: 한 부하 시험의 A 검색 P95가 약 **11.42초**까지 증가했고, B/C는 정상 응답을 유지했습니다. 이 값은 모든 실행에서 동일한 상수가 아닙니다.

## 3. 복구 및 사건 종료

- 정해진 k6 시험이 종료되면 유입 부하가 감소
- A CPU/응답시간이 정상 수준으로 회복
- Prometheus CPU 경보 정상 상태 확인
- SCHUTZ 관리 웹에서 복구 상태를 확인한 뒤 **관리자가 수동으로 사건 종료**
- Slack 복구 알림과 사건 종료 기록을 각각 구분하여 확인

> **핵심 구분**
> - 부하 종료에 따른 자연 복구: 애플리케이션 상태 정상화
> - Prometheus 알림 정상화: 모니터링 경보 상태 정상화
> - 관리자 사건 종료: 사건 처리 기록 종료
>
> 사건 종료만으로 실제 서비스가 복구되거나 공격이 차단되는 것은 아닙니다.

## 4. 수동 장애 조치 시나리오 확장 시 유의점

추가로 엔지니어 수동 조치를 증명하고 싶다면, **기존의 안전장치가 유지되는 격리 테스트 환경**에서 인위적으로 지속되는 부하의 원인을 확인하고 직접 완화하는 단계가 필요합니다. 예: 승인된 테스트용 부하 프로세스 식별, 작업 중단, 요청 제한 적용, 자원 조정 후 재검증.

실행 중인 운영 서비스를 임의로 재시작하거나 무제한 부하를 걸지 않습니다. 최대 실행 시간, CPU/메모리 제한, 긴급 중단 절차를 반드시 유지합니다.

## 5. 남은 확인 항목(팀원분 요청)

- [ ] B `/api/organization`의 P95·RPS·5xx 값이 의도한 시간 범위에 나타나는지 확인
- [ ] C `/api/questions`의 P95·RPS·5xx 값이 같은 범위에 나타나는지 확인
- [ ] CPU 사고 시각 **2026-11-16 23:47:01 KST**의 붉은 점선 표시 확인
- [ ] 테스트 CPU 지표 4개(직원 포털 A 정상/부하, B, C)와 수집 시점 확인

이 체크리스트는 이미 검증한 CPU 장애 생명주기와는 별개인 **팀 대시보드 QA** 항목입니다.
